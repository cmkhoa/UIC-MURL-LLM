# Controlled cross-family comparison: preparation after v0.4

Status: protocol draft, not executed. No test evaluation is authorized by this
protocol alone. v0.4 has not demonstrated a satisfactory correctness/taxonomy
balance, so freeze a candidate training recipe before starting this comparison.

## Candidate families

Use Qwen2.5-3B-Instruct as the existing anchor. Shortlist
[Meta Llama-3.2-3B-Instruct](https://huggingface.co/meta-llama/Llama-3.2-3B-Instruct)
and [Microsoft Phi-3.5-mini-instruct](https://huggingface.co/microsoft/Phi-3.5-mini-instruct)
as two other instruction-tuned families. These are proposed experimental
comparators, not claims about relative grading quality. Official model cards
were checked on 2026-10-24. Confirm access and compatible local loading, then
record immutable model/tokenizer revision hashes before any validation run.
Do not substitute a model after seeing its validation results.

## Freeze before execution

- One training JSONL and provenance manifest, built only from train; one
  unchanged v0.2 system prompt. Apply exactly the same recipe across families.
- The existing 48-example validation split and evaluator revision. No held-out
  test data in any model-selection or debugging input.
- Seed 20261004; NF4/FP16 QLoRA; rank 8, alpha 16, dropout 0.05; 60 steps;
  effective batch size 8; learning rate 0.0002; warmup 3; sequence cap 2048.
  This matches optimizer updates and examples, not FLOPs or token counts.
  Report each model's token counts, trainable parameters, GPU time, and memory.
- Model-native chat templates with the same messages and canonical JSON targets;
  assistant-only loss. Inspect truncation on train only. Do not silently shorten
  prompts for a model or change the cap after seeing validation scores.
- Inspect architecture module names and target equivalent attention/MLP linear
  projections. Fused projections require a documented mapping; identical rank
  does not imply identical trainable parameter count across architectures.
- Greedy decoding, maximum 256 new tokens, one response per validation example,
  no retries or output-repair heuristics. Record native EOS/padding behavior.
- Each family gets its own untouched base control under exactly the same prompt,
  tokenizer/template, quantization, and decoding as its adapter.

Run train-only loading/tokenization/adapter smoke checks before validation.
If a family cannot fit the frozen setup, report it as infeasible rather than
giving it a private tuning budget. Pin software versions and inspect any
required remote model code before executing it.

## Decision and reporting

Before running, adopt and commit one explicit multi-metric selection rule.
Suggested rule: require at least 47/48 valid outputs and correctness macro F1
at least the frozen v0.2 anchor (0.493); among eligible adapters, maximize
taxonomy macro F1, breaking exact ties by first-error exact match and then
correctness accuracy. If none qualifies, select no final model. These are
prospective proposed criteria, not a retrospective significance test of v0.4.

Report all candidates, base-to-adapter changes, validity, valid-only quality,
correctness success over all 48 examples, per-label support, confusion counts,
and localization denominators. Treat small differences and one-example rare
classes cautiously. Any further seeds must be predeclared and applied equally
to all compared candidates; do not select a lucky seed.

After the candidate recipe and cross-family winner are frozen, save the exact
checkpoint/config hashes and one final test-evaluation plan. Only then evaluate
that single final model once on held-out test; do not tune against its results.
