# v0.8 paired v0.5/v0.7 cross-family execution plan

## Purpose

Compare instruction-model families under both the frozen v0.5 moderated
taxonomy-balance recipe and the completed v0.7 two-stage continuation. The
objective is to determine both whether another base family improves the
complete grading task and whether v0.7's late diagnosis phase transfers beyond
Qwen without sacrificing v0.5's taxonomy strength.

This amendment was committed after the Qwen v0.5 and v0.7 results were known
but before any Llama or Phi validation result was observed. It is a
validation-only, paired recipe-by-family comparison. It does not introduce a
new prompt, dataset, sampling policy, or optimization setting beyond the two
already frozen recipes.

## Precommitted candidate set

Use these three families in this order:

1. **Qwen2.5-3B-Instruct** — the existing v0.5 and v0.7 anchors.
2. **Llama-3.2-3B-Instruct** — a same-scale, different-family comparator.
3. **Phi-3.5-mini-instruct** — a compact comparator with a different training
   profile.

For each family, compare two recipe arms:

1. **v0.5:** ordinary assistant-only SFT for 60 steps on the frozen moderated
   taxonomy-balanced training data.
2. **v0.7:** 30 ordinary v0.5 steps, followed by a checkpointed continuation
   for 30 steps with `first_error_step` and `error_taxonomy` weighted 2× and
   all other assistant tokens weighted 1×.

Reuse the completed Qwen v0.5 and v0.7 results and artifacts; do not rerun them.
For Llama and Phi, run the untouched base control once and both recipe arms.
This leaves four new training runs and six new validation passes: one base and
two adapters for each of the two untested families.

Before the first validation inference for a family, record its immutable
model and tokenizer revisions, license/access status, chat template,
architecture module mapping, parameter count, and software versions. A model
that cannot be loaded or fit under the frozen setup is reported as infeasible;
it is not replaced after another family's validation score is known.

## Frozen inputs and controls

Both recipe arms for every feasible family use:

- `data/training/v0.5-sft-train.jsonl` and its provenance metadata only;
  the generator reads only `data/processed/train.jsonl`.
- The v0.2 SFT system prompt, canonical JSON targets, and model-native chat
  template. Assistant-only loss is required.
- Seed `20261004`; NF4/FP16 QLoRA; rank 8; alpha 16; dropout 0.05; learning
  rate 0.0002; warmup 3; effective batch size 8; maximum sequence length 2048;
  and exactly 60 optimizer steps. v0.5 uses ordinary loss for all 60 steps;
  v0.7 uses the frozen 30+30 loss schedule and checkpoint reload.
- Equivalent attention and MLP linear-projection targets for each architecture.
  Document fused-projection mappings and trainable parameter counts.
- The fixed 48-example validation split, greedy decoding, 256 maximum new
  tokens, one output per example, no retries, and no output repair.

Run one untouched base-model control before either adapter evaluation for each
new family, using the same prompt, template, quantization, and decoding. Train
both arms independently from the same untouched base revision; v0.7 does not
start from the completed v0.5 adapter. Inspect tokenization, truncation, adapter
attachment, field masks, checkpoint resume, and schema-valid smoke outputs
using training data only before validation. A setup failure before any
validation output may be repaired and restarted with the repair documented; a
completed validation run is never rerun for a better score.

The held-out test split must not be read, tokenized, or used for debugging at
any stage of this plan.

## Execution sequence per new family

1. Mount Drive and set
   `HF_HOME=/content/drive/MyDrive/MURL/huggingface-cache`.
2. Resolve the pinned model revision from the persistent cache; if needed,
   copy it to local runtime storage and verify weight files before loading.
3. Run and archive the untouched base control on validation once.
4. Train the v0.5 arm for 60 ordinary SFT steps, reload it, and evaluate it
   once on validation.
5. Independently train the v0.7 arm for 30 ordinary steps, save and reload the
   Stage 1 checkpoint with optimizer/scheduler state, continue for 30 weighted
   steps, reload the final adapter, and evaluate it once on validation.
6. Save the source snapshot, both model/training ZIPs, base-control ZIP, both
   adapter-validation ZIPs, and full executed notebooks under both
   `runs/baseline/` and Drive.
7. Verify each ZIP with `unzip -tq`, compare local and Drive SHA-256 hashes,
   stop the T4 session, and record the results in a versioned report.

## Prospective paired analysis and selection rule

Report the v0.7-minus-v0.5 change within each family for validity, correctness,
taxonomy macro F1, first-error exact match, first-error MAD, and balanced
utility. This paired analysis is required even when one or both arms are
ineligible; it tests whether the recipe effect is consistent across families.

For final model selection, apply one uniform eligibility gate to every arm. An
adapter is eligible only if it produces at least 47/48 schema-valid outputs,
correctness over all 48 is at least 30/48, taxonomy macro F1 is at least
`0.3201`, and first-error exact match is at least 53.6%. These component floors
are the already precommitted v0.7 thresholds derived from the frozen v0.5 Qwen
anchor, not thresholds chosen from the completed v0.7 result. Compute the
unweighted balanced utility for every arm:

```
utility = (correctness_accuracy_all_48
           + taxonomy_macro_f1_valid_only
           + first_error_exact_match_valid_only) / 3
```

Within each family, nominate the eligible arm with the higher utility. If only
one arm is eligible, nominate it; if neither is eligible, that family has no
nominee. The completed Qwen v0.7 arm remains ineligible because its taxonomy
macro F1 was `0.3029`, so this amendment does not retroactively overturn its
precommitted decision.

Select the family nominee with the highest utility. Break an exact tie using,
in order: taxonomy macro F1, first-error exact match, then correctness accuracy.
Report all components and denominators; utility does not replace the component
metrics. If no arm is eligible, select no final model and do not evaluate the
held-out test set.

Small differences must be interpreted cautiously because validation has 48
examples and several taxonomy labels have one example. The v0.3–v0.5 error
review remains the qualitative context for the selection.

## Deliverables and gate to held-out test

Publish one report per family/recipe arm plus a consolidated paired comparison
report with base-control results, all adapter metrics, within-family recipe
deltas, per-label support and confusions, topic/difficulty slices,
token/truncation statistics, trainable parameters, runtime, and artifact
hashes.

After a winner is selected, commit a final-test plan naming its exact adapter,
base revision, prompt, decoder, evaluator revision, and archive hashes. Only
that frozen adapter may be evaluated once on the held-out test split. No result
from the held-out test may trigger another tuning round.
